# 入口有界性审查（P0）

数据库侧有界只是最后一道。若入口接受任意 `pageSize`、任意长度的数组、任意时间范围，下游要么被迫全量查询，要么被迫拒绝合法请求，两种都会炸库或炸内存。本页按入口类型给出判据；出口侧见 `templates/database-review.md`。

## 必须显式有界的五个维度

| 维度 | 典型位置 | 上限参考 | 缺失后果 |
| :--- | :--- | :--- | :--- |
| 条数 | `pageSize`、`limit`、`size`、`count` | 列表 200 以内；导出按批 1000 以内 | 全表扫描、大结果集驻留内存 |
| 集合长度 | 请求体中的 id 数组、批量接口、`in` 条件 | 元素 100~500，超出拒绝或分批 | SQL 过长、参数栈溢出、堆膨胀 |
| 体积 | 请求体、上传文件、大文本字段 | body 1~10 MB，单字段按业务定 | OOM、GC 抖动 |
| 时间窗 | 报表、日志、流水查询的 `from`/`to` | 最大跨度 7~31 天 | 范围扫描击穿索引 |
| 并发与深度 | 同 key 并发、嵌套 JSON、目录遍历、递归展开 | 并发数按容量定；深度 8~16 | 连接池耗尽、栈溢出 |

## 按入口类型检查

### HTTP controller / action

1. 分页参数是否有硬上限（DTO 校验、拦截器或框架配置），而不只是给默认值。
2. 排序字段是否白名单校验；禁止把前端传入的列名直接拼进 `order by`。
3. 列表接口是否存在“缺省不分页、返回全量”的路径。
4. 导出/下载是否流式写出，是否同时限制条数与时间窗。
5. 单次请求是否会触发多次下游调用（循环 RPC、N+1 查询）——这类放大比单条大查询更危险。

### RPC / TCP / 自定义协议

1. 报文长度前缀是否有上限，反序列化前是否校验实际长度（防半包堆积与超大帧）。
2. 单连接未读完的数据是否有超时与缓冲区上限。
3. 批量命令的批次大小是否有上限，是否允许一次提交任意条。

### MQ 消费者

1. 是否按批拉取，批大小与单条消息体积是否有上限。
2. 消费失败重试次数是否有上限、是否有死信队列。
3. 是否存在“消费一条消息 → 查询全量/全表”的写法。

### CLI / 定时任务

1. 是否提供 `--all` 之类无上限开关，是否有条数或时间窗保护。
2. 定时任务是否分片执行，单次处理条数是否设上限。
3. 是否存在对全表扫描且无时间窗的批处理。

## 审查动作

1. 枚举入口清单：controller/action 方法、RPC handler、MQ listener、CLI 命令、定时任务。
2. 对每个入口逐项标注五维度：条数、集合长度、体积、时间窗、并发与深度；缺哪项记哪项。
3. 对外接口缺失判 P0，内部脚本或运维工具缺失判 P1；报告中写明“改前判断点”与“改后上限值”。
4. 入口不可控时（第三方回调、外部推送），要求网关层限流与体积上限，并在报告注明该依赖。

## 豁免

1. 按 ID 或唯一键返回单条的详情接口。
2. 健康检查、指标、就绪探针等固定小响应端点。
3. 上限由网关或框架统一强制，且可在配置或拦截器中验证的入口——需在报告里给出该配置位置。

## 与查询有界的关系

入口有界是闸门，查询有界是兜底。判定口径：

| 入口有界 | 查询有界 | 结论 |
| :--- | :--- | :--- |
| 是 | 是 | 通过 |
| 是 | 否 | 查询侧 P0（入口合法，但大跨度请求仍可能拖垮库） |
| 否 | 是 | 入口侧 P0（查询虽有 LIMIT，但入口可绕过限制或制造海量小查询） |
| 否 | 否 | 入口侧 P0，并同时给出查询侧修复建议 |
