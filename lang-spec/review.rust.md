# Rust 代码审查规则

> 本文件面向代码审查，聚焦 Rust 特有的缺陷模式与审查动作。
> 编码约束以 `${AI_SPEC_ROOT}/lang-spec/spec.rust.md` 为准，通用审查框架以 `${AI_SPEC_ROOT}/skills/code-review/SKILL.md` 为准。

## 严重度口径

与 `code-review` 统一为三级，禁止使用其他分级：

| 级别 | 判定标准 | 处理要求 |
|------|----------|----------|
| P0 | 未定义行为、安全漏洞、数据错误、进程崩溃、资源泄漏 | 本次修改必须修复 |
| P1 | 并发隐患、错误处理缺陷、性能退化、可维护性问题 | 下次迭代修复并登记 |
| P2 | 风格、命名、文档、可选优化 | 选择性修复 |

## 静态分析工具

审查前先执行自动化检查，人工审查聚焦工具无法覆盖的语义问题：

```bash
cargo fmt --all -- --check          # 格式
cargo clippy --all-targets -- -D warnings   # 缺陷与惯用法
cargo test --all-targets            # 行为验证
cargo audit                         # 依赖漏洞
cargo deny check                    # 许可证与依赖策略
```

补充工具：`cargo miri test`（unsafe 与未定义行为）、`cargo llvm-cov`（覆盖率）、`cargo flamegraph`（性能热点）。

## 正确性审查

- **panic 路径**：生产代码中的 `unwrap()`、`expect()`、`panic!`、`todo!()`、`unimplemented!()`、数组下标越界均为 P0 候选；测试代码与明确不可恢复的启动断言除外，但必须写明理由。
- **整数运算**：`+ - *` 在 release 下溢出会回绕，涉及金额、计数、长度时使用 `checked_*`、`saturating_*` 或 `overflowing_*`。
- **类型转换**：`as` 截断（如 `u64 as u32`、`f64 as i64`）必须确认取值范围，必要时使用 `TryFrom`。
- **切片与索引**：直接索引 `v[i]` 前必须确认边界，优先使用 `get()`、`get_mut()`。
- **模式匹配**：`match` 不得使用 `_ => {}` 吞掉未处理分支，除非该分支确实无需处理并附注释。

## 所有权与生命周期审查

- **不必要的克隆**：循环内、热路径上的 `.clone()` 必须说明理由；能借用则借用，能 `Cow` 则 `Cow`。
- **参数类型**：函数参数优先 `&str`、`&[T]`、`&T`，而不是 `String`、`Vec<T>`、`T`。
- **生命周期逃逸**：不得为了绕过借用检查使用 `Box::leak`、`mem::transmute`、`'static` 强制转换。
- **循环引用**：`Rc`/`Arc` 相互持有必须用 `Weak` 打破，否则为 P0 内存泄漏。
- **内部可变性**：`RefCell`/`Cell` 使用处必须确认不存在跨线程共享与借用冲突。

## 错误处理审查

- **错误丢失**：`let _ = result;`、`.ok();`、`if let Ok(..)` 丢弃错误分支，必须确认是否应记录或传播。
- **错误类型**：库代码使用 `thiserror` 定义明确错误类型；应用入口可使用 `anyhow`，但不得在库边界泄露 `anyhow::Error`。
- **错误上下文**：`?` 传播时补充上下文（`context()` 或 `map_err`），避免错误信息丢失调用场景。
- **Option 与 Result 混用**：可恢复错误不得降级为 `Option`，否则丢失失败原因。

## 并发与异步审查

- **阻塞调用**：异步任务中禁止 `std::thread::sleep`、同步文件 I/O、同步数据库驱动等阻塞操作，应使用异步版本或 `spawn_blocking`。
- **跨 await 持锁**：不得在 `.await` 前后持有 `std::sync::Mutex` 守卫，改用 `tokio::sync::Mutex` 或缩短临界区。
- **任务泄漏**：`tokio::spawn` 的句柄必须被等待或显式 detach，并说明生命周期与取消策略。
- **锁顺序**：多处加锁必须固定顺序并注释，避免死锁。
- **Send/Sync 边界**：`unsafe impl Send/Sync` 必须有安全论证，否则为 P0。
- **取消安全**：`select!` 分支中的 future 必须可取消，不得在取消后留下不一致状态。

## 内存与 unsafe 审查

- **unsafe 块**：每个 `unsafe` 块必须有 `// SAFETY:` 注释，说明前置条件与不变量；缺失注释为 P0。
- **未定义行为**：检查裸指针解引用、`transmute`、`get_unchecked`、`from_raw_parts` 的长度与对齐约束。
- **资源释放**：`mem::forget`、`ManuallyDrop` 必须有明确理由，否则视为资源泄漏。
- **FFI 边界**：C 互操作处检查空指针、所有权转移与字符串编码。

## 性能审查

- **热路径分配**：循环内 `format!`、`to_string()`、`collect()`、`Vec::new()` 反复分配，应复用缓冲区或预分配 `with_capacity`。
- **迭代器使用**：优先迭代器链，但避免为"优雅"构造多层 `flat_map`/`filter` 导致的额外开销；以基准数据为准。
- **字符串拼接**：多次拼接使用 `String::with_capacity` 或 `write!`，避免反复扩容。
- **锁粒度**：锁内不得执行 I/O、序列化或耗时计算。
- **基准验证**：性能改动必须提供 `cargo bench` 或火焰图前后对比，不接受无数据的"更快"结论。

## 安全审查

- **依赖风险**：新增依赖必须通过 `cargo audit` 与 `cargo deny check`，并说明引入理由。
- **反序列化**：不受信任输入的反序列化必须限制大小与深度，避免 DoS。
- **命令执行**：`Command` 不得拼接未校验的用户输入，禁止经 shell 间接执行。
- **敏感信息**：密钥、令牌不得硬编码，不得出现在日志与错误信息中。
- **加密随机**：安全场景使用 `rand::rngs::OsRng` 或 `getrandom`，禁止使用可预测种子。

## 代码质量与坏味道

- **文件长度**：建议不超过 500 行，超过 1000 行必须拆分，并在报告中说明结构性阻碍。
- **变量声明**：禁止同一行多条 `let` 声明，每个变量独占一行；解构赋值不视为多声明。
- **模块边界**：`pub` 暴露面最小化，内部实现使用 `pub(crate)`；禁止为方便测试扩大公开 API。
- **注释**：文件、模块、公开项必须有文档注释；复杂安全逻辑与不变量必须有行内说明。
- **重复代码**：相同逻辑出现三次以上应抽取函数或 trait，但避免为消除重复引入过度抽象。

## 审查优先级

| 优先级 | 审查内容 |
|--------|----------|
| 必须修正（P0） | unsafe 无安全论证、未定义行为、panic 路径、循环引用泄漏、并发数据竞争、安全漏洞 |
| 应当修正（P1） | 错误丢失、阻塞异步、任务泄漏、热路径分配、不必要的 clone、公开面过大 |
| 建议改进（P2） | 命名、文档、迭代器写法、容量预分配、注释完善 |

## 审查输出

按 `code-review` 的报告模板输出，每条问题必须包含：级别、文件与行号、问题描述、影响、修复建议、验证方式。Rust 项目额外附上 `cargo clippy` 与 `cargo test` 的执行结果。
